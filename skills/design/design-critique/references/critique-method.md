# Task-led critique

First establish the audience, decision, page purpose, constraints and success signal. Inspect the rendered first viewport and at least one complete task flow, including a narrow viewport and a failure/empty state when relevant. Describe observation before interpretation: “The destructive Delete button uses the same weight and adjacent placement as Save” is observable; “users will delete accidentally” is a hypothesis that needs testing.

Use a hierarchy pass: identify dominant element, scan path, information scent, grouping, action priority and competing emphasis. Then a comprehension pass: can a new user explain labels, numbers, units and consequences without hidden context? Finally inspect feedback: loading, validation, success, permission denial and recovery. Check whether the UI makes the next safe action evident.

Example: an occupancy dashboard leads with a decorative illustration while a stale occupancy value and unresolved room exceptions sit below the fold. Recommend moving the freshness label and exception count alongside the lead metric, reducing illustration prominence, and linking the exception to its filtered table. Verify that a reviewer can identify current status, uncertainty and next action in a timed task with the same data fixture. This is a hypothesis about usability until tested.

Avoid generic advice such as “add whitespace” without naming which relationship becomes clearer. A brand choice that differs from personal taste is not a defect unless it obstructs the stated task or violates a constraint.
