# MVCC, isolation and transaction correctness

PostgreSQL MVCC gives statements snapshots, but the snapshot boundary depends on isolation level. Under Read Committed, successive statements may see different committed data; Repeatable Read holds a transaction snapshot; Serializable can abort a transaction with SQLSTATE `40001`, so the **whole** transaction must be retried safely. PostgreSQL treats Read Uncommitted as Read Committed. Confirm these semantics in the installed major version's [transaction isolation documentation](https://www.postgresql.org/docs/current/transaction-iso.html).

Example: two workers read an account balance of 10 and each decides to reserve 7. A read-then-write check outside one protected transaction can oversubscribe. Prefer an invariant enforced atomically, for example an `UPDATE accounts SET available = available - 7 WHERE id = $1 AND available >= 7 RETURNING available` in an authorized fixture, combined with constraints and application handling for zero rows. A check constraint alone may not cover cross-row invariants. With Serializable isolation, retry `40001` from the transaction start using an idempotency key for external side effects.

Draw a schedule with T1/T2 statements, snapshots, lock acquisitions and commit/abort. Test two concurrent sessions and assert the final business invariant, not just absence of errors. Long-lived snapshots can delay cleanup and contribute to bloat; inspect idle-in-transaction patterns before changing vacuum settings. WAL durability and crash recovery differ from transaction isolation; a committed result still needs the system's backup/replication design for disaster recovery.
